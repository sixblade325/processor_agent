# 可运行产品与实验资产边界

状态：当前交付边界  
日期：2026-09-02

## 1. 文档职责

本文细化 [V3 产品计划](PRODUCT_PLAN.md) 中可运行产品、执行支撑层和实验资产的边界，作为近期产品实现与发布验收的工作基线。

产品定位、Skill 职责和整体范围仍由 V3 产品计划统一定义。本文只负责回答两个问题：

1. 当前还缺少哪些内容，产品才能被安装和运行。
2. 哪些内容用于验证产品效果，不构成产品运行条件。

## 2. 当前判断

Processor Agent V3 已经具备主要的处理器领域 Skill。当前可运行产品缺少五项薄配件：

1. Codex plugin manifest。
2. 环境与工具链契约。
3. `doctor` 和固定工具入口。
4. 可复现安装包。
5. 工具级测试。

以下三项属于实验资产：

1. Skill 行为 eval。
2. 最小处理器示例。
3. A/B 对照演示。

实验资产用于证明触发质量、方法有效性和产品收益。删除实验资产后，已安装产品仍应能够正常运行。

## 3. 可运行产品

### 3.1 Codex plugin manifest

Codex plugin manifest 负责声明产品身份、版本、Skill 路径、界面元数据和安装入口。它只接入 Codex 已有运行能力，不注入独立会话系统或任务调度器。

### 3.2 环境与工具链契约

环境与工具链契约应明确：

1. 必需工具和可选工具。
2. 支持的版本范围。
3. Windows、WSL 和 Linux 的职责边界。
4. 工具探测方式。
5. 开源工具的可复现安装方式。
6. Vivado 等专有工具的外部安装、许可证和接入边界。
7. 缓存、日志和生成文件的位置。

该契约只描述运行条件，不保存处理器架构事实。环境探测、安装、配置和平台适配通过确定性脚本实现，`bootstrap-processor-project` 不承担这些职责。

### 3.3 `doctor` 和固定工具入口

Agent 不应为每次任务重新搜索工具、猜测命令、处理平台转义或扫描完整日志。产品应提供稳定、可发现的机械入口，例如：

```text
doctor
check-docs
elaborate
compile
test
simulate
collect-vivado-timing
package
```

具体命令集合由实现阶段根据现有 Skill 的真实依赖收敛。每个入口应尽量支持明确的项目根目录、结构化输出、退出码、工具版本和证据路径。

### 3.4 可复现安装包

安装包应从指定 Git commit 构建，并满足：

1. 文件集合明确。
2. 不包含缓存、实验运行结果和历史草案。
3. 记录版本和内容 hash。
4. 相同输入能够生成相同内容。
5. Skill 所需运行脚本和参考材料完整。
6. 安装和卸载步骤可由用户直接执行。

### 3.5 工具级测试

工具级测试负责检查：

1. plugin manifest 和包结构。
2. 环境探测结果。
3. 平台路径和命令转发。
4. 结构化输出与退出码。
5. 缺失工具和错误配置的诊断。
6. 安装包文件集合与可复现性。

这些测试属于产品发布门禁。它们通常不进入最终安装产物。

## 4. 执行支撑层

上述薄配件共同构成 `Execution Support Kit`。它负责降低末端 Agent 调用外部工具时的重复探索、错误调用和上下文消耗。

执行支撑层可以：

1. 探测工具和版本。
2. 选择已登记的工具路径。
3. 规范命令参数和工作目录。
4. 管理缓存、日志和运行产物。
5. 输出可追踪的结构化结果。
6. 为 Skill 提供稳定的确定性工具入口。

执行支撑层不负责：

1. 决定当前工程任务。
2. 调度 Agent 或 subagent。
3. 维护 Stage、Task、Run 或 Approval 状态。
4. 作出处理器架构判断。
5. 接受或拒绝候选修改。
6. 保存第二份处理器模型。
7. 覆盖用户项目中的命令和事实。

Skill 决定需要取得什么证据，Agent 决定何时调用工具并解释结果，执行支撑层完成机械执行，设计师作出架构取舍。

## 5. 源仓库与安装产物

产品源仓库的目标结构为：

```text
processor-development-skills/
├── .codex-plugin/
├── README.md
├── LICENSE
├── skills/
├── tools/
├── environment/
├── scripts/
└── tests/
```

最终安装产物只包含运行所需内容：

```text
.codex-plugin/
skills/
tools/
environment/
scripts/
README.md
LICENSE
```

具体文件白名单由打包脚本和工具级测试共同约束。

## 6. 实验资产

实验资产独立组织：

```text
experiments/
├── evals/
├── examples/
└── comparative-evaluation/
```

### 6.1 Skill 行为 eval

检查 Skill 是否在正确条件下触发，是否改变 Agent 行为，以及关键约束在真实会话中是否得到遵守。

### 6.2 最小处理器示例

为行为评测和演示提供固定输入，不成为产品支持的处理器模板或第二份处理器模型。

### 6.3 A/B 对照演示

按照 [Skill Package 对照评测方案](SKILL_PACKAGE_COMPARATIVE_EVALUATION.md) 比较 Control Team 和 Skill Team，用于形成比赛演示和效能证据。

实验失败会形成产品改进输入。实验尚未执行不阻止可运行产品完成安装与基础功能验收。

## 7. 近期实现顺序

当前产品开发主线依次完成：

1. Codex plugin manifest。
2. 环境与工具链契约。
3. `doctor` 和首批固定工具入口。
4. 可复现打包流程。
5. 工具级测试和发布验收。

完成可运行产品后，再独立推进 Skill 行为 eval、最小处理器示例和 A/B 对照演示。

## 8. 可运行产品验收

1. 用户可以按照 `README.md` 安装和卸载 Codex plugin。
2. Codex 可以发现并调用全部正式 Skill。
3. `doctor` 能准确报告必需工具、可选工具、版本和缺失项。
4. Skill 使用的重复性工程命令具有固定入口。
5. Windows、WSL 和 Linux 的执行边界明确。
6. 运行产物进入规定的 `.runtime/` 或项目指定目录。
7. 安装包能够从固定 commit 重复构建并校验内容 hash。
8. 工具级测试全部通过。
9. 删除 `experiments/` 后，产品仍能完成安装、环境检查和 Skill 调用。
10. 产品运行不依赖 V1 或 V2 Harness 状态。
