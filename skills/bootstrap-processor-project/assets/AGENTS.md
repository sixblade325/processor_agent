# 通用处理器项目 Agent 协作规则

本文件由 `bootstrap-processor-project` 使用固定基线初始化。写入用户项目后，由该项目维护。用户可以直接调整规则、路径和命令。Skill Package 的后续更新不得自动覆盖项目中的 `AGENTS.md`。

## 0. 初始化边界与项目映射

1. `bootstrap-processor-project` 只负责生成或提议更新项目级 `AGENTS.md`。
2. 已有 `AGENTS.md` 时保留原文件。新增、删除或改写规则前，先向用户展示差异并取得确认。
3. 环境探测、安装、配置、工具路径解析和平台适配由脚本负责，不属于 `bootstrap-processor-project`。
4. 默认项目映射如下。实际路径不同时，经用户确认后修改本节，后文继续使用这些语义名称。

```text
Architecture: Architecture/
Design:       Design/
Source:       src/
Verification: Verification/
Runtime:      .runtime/
```

5. 项目应在本节补充正式的构建、测试、仿真、综合和静态检查脚本入口。没有正式入口时，Agent 先读取仓库现状并向用户报告缺口。

## 1. 最高优先级

1. 用户对当前任务的明确指令决定任务目标、授权范围和交付形式。
2. 用户明确作出的项目决定与当前 Git 权威材料共同构成正式依据。用户后续的一般表述视为修改意图。只有用户明确声明替换既有事实时，才更新对应正式事实。
3. 回答任何用户问题前，先读取直接相关的设计文档、源码、测试或本地协作约束。
4. 目标性质以已确认的 Architecture 为准，具体设计以当前 Design 为准，当前实现以 Source 和 Verification 证据为准。
5. 写代码前必须读取直接相关的 Architecture、Design、Source 和 Verification 材料。
6. 未完成相关材料读取和源码追踪时，不输出确定性技术结论。
7. 禁止使用“大概率”“可能”“猜测”“估计”等无依据措辞替代核验。
8. 无法核验时，直接说明缺少哪个文件、代码路径、信号、工具输出或输入条件，并停止给出确定性结论。
9. 回答和人类可读文档默认使用中文。信号名、模块名、字段名、文件名、命令和代码保持英文。
10. Windows PowerShell 读取 UTF-8 文档时必须使用 `Get-Content -Raw -Encoding utf8 -LiteralPath <path>` 或项目声明的等价 UTF-8 入口，不得依赖默认编码。
11. 永远不要使用先否定 A 再转折替换为 B 的中文对照句式。不要出现破折号。
12. 不使用先模糊认可再转折纠错的套话。错了就直接说明错在哪。
13. 回答客观、直接、服从用户当前目标。零吹捧，零情绪。
14. 除非用户明确要求状态，否则不发送中途状态回报，不描述正在执行或将要执行的动作。完成后直接交付结果。
15. Agent 的建议、草案、默认项和推断均不等于用户决定，不得标记为已确认或已批准。
16. 不扩大用户授权的任务范围。写权限、外部副作用或破坏性操作不明确时，先取得用户授权。

## 2. 事实权威与维护权

发生冲突时按以下顺序核对：

1. 用户已明确作出且适用于当前基线的决定。
2. Architecture 中已确认的处理器目标、性质、约束、Contract 和 ADR。
3. Design 中当前有效的模块、接口、协议、生命周期和周期语义。
4. Source 与 Verification 所证明的当前实现行为。
5. Research、Review、Finding 和实验材料。
6. 通用 Skill、外部项目和经验性惯例。

维护规则：

1. Architecture 由用户作出最终决定。Agent 可以研究、比较、质疑和起草，不能自行批准架构事实。
2. Design 由用户与 Agent 共同维护，负责把 Architecture 落实到拓扑、模块、字段、接口、状态、周期和验证点。
3. Source 与 Verification 是正式项目资产。实现修改应关联当前 Design 和可执行验收条件。
4. Research、Review、Finding 和实验结果提供证据，不直接覆盖 Architecture 或 Design。
5. Skill 定义工作方法，不保存项目专属事实，也不覆盖项目内权威材料。
6. 同一规范性事实只保留一个完整定义。其他位置使用摘要和链接。
7. 发现冲突时，分别说明目标架构、当前设计、当前实现、验证证据和迁移影响。

## 3. 任务权限与用户交互

1. 回答、解释、Review 和诊断任务默认只读。用户明确要求修改或实现时，才写入项目文件。
2. 修改任务只触及当前目标所需的文件。发现相邻问题时记录为未解决问题，不顺带扩大改动。
3. 用户提供的代码片段、接口和优先级属于实现输入。发现其中存在语法、类型、周期或语义错误时，先指出具体位置、反例和影响。
4. 需要用户作出架构取舍时，给出选项、证据、代价和待确认问题，等待用户决定后再落实。
5. Review 结论必须绑定明确的文件、Git commit 或工作树基线。Revise 必须明确列出准备修改的事实与文件。
6. 未经用户明确要求，不删除现有文件，不清理历史产物，不重排项目拓扑，不改动仓库外部状态。

## 4. Architecture 与 Design 门禁

1. Architecture 表达处理器目标、可观察性质、范围、约束、取舍和验收条件，不承载模块内部实现细节。
2. Design 表达当前微架构，包括拓扑、模块职责、接口、协议、Lifecycle、ADR、周期行为和验证映射。
3. 修改 Source 前，相关 Architecture 要求与 Design 约束必须足以支持实现。缺项会影响正确性时，先闭合缺项。
4. 新增处理器性质、状态字段、跨模块接口、流水级、generation、tag、身份保护或宽泛串行化机制前，必须取得用户确认。
5. 每项设计结论必须说明字段、生产者、寄存边界、消费者、副作用和不变量。
6. 每个状态字段必须说明设置、保持、清除、释放、复用和 reset 行为。
7. 每个跨模块协议必须说明请求与响应规则、背压、stall、flush、redirect、kill、retry、迟到 response 和索引复用。
8. 同拍事件必须给出完整优先级，并集中表达仲裁关系。
9. 正确性约束、性能目标、时序代价、面积代价和验证成本必须分开表述。
10. Chisel 接口文档按照 `Scala declaration -> semantics` 的顺序组织。Scala 只保留表达接口所需的最小片段，字段语义按照声明顺序解释。
11. 实现中发现全局架构、接口或正确性缺口时，停止受影响的修改，将证据和待决问题返回 Architecture 或 Design。

## 5. 实现约束

1. 使用源码搜索追踪定义、生产端、寄存边界、消费端和副作用。
2. 实现前提炼当前任务的字段语义、事件表、不变量和验收标准。
3. 修改范围保持最小，优先复用现有结构、字段和命名。
4. 禁止自行补字段、补协议、补身份保护或扩大保守机制。
5. 按硬件结构分析 Chisel，检查事件、mask、one-hot、寄存边界、扇出、组合深度和关键路径。
6. 多写口更新先形成事件或写使能，再集中仲裁。同拍冲突优先级不得散落在多个位置。
7. `Mux1H` 输入必须满足 one-hot 或 zero-hot，并添加对应断言。
8. 发射、选择和 forwarding 路径只 mux 必需字段，避免无依据的整包宽 Bundle mux。
9. 所有 `for`、`map`、`fold`、`reduce`、递归和多端口分配逻辑都要判断综合结果属于并行网络或依赖链。
10. 引入优先译码链、高扇出控制、宽比较网络或长距离组合 forwarding 时，必须说明结构、规模、时序风险和替代方案。
11. 不依赖 Scala 源码层级保证 FPGA 布局。需要硬时序边界时使用寄存器，并同步相关 Design。
12. 每个由项目自主维护的 `.scala` 源文件都必须在同目录维护 `<SourceBase>_codex.md`。
13. Agent 创建或修改 `.scala` 源文件时，必须在同一变更中创建或更新对应 `_codex.md`。
14. `_codex.md` 只摘要源码职责、接口语义、事件优先级、状态生命周期、周期边界、断言、验证证据、时序风险和未验证行为，不能覆盖 Architecture 或 Design。
15. 生成代码、第三方代码和供应商代码默认不要求 `_codex.md`，除非项目明确将其纳入自主维护范围。

## 6. Verification 与工程证据

1. 每个修改都要有可执行验收条件，具体到输入、事件、信号、周期和预期副作用。
2. 编译通过只证明构建成立，不能替代功能验证。
3. 验证至少覆盖正常路径、边界条件、同拍冲突、stall、flush、kill、retry、迟到 response、索引复用和 reset 中与任务相关的部分。
4. 测试失败时记录测试名、复现命令、工具版本、随机种子、失败周期、关键输入、实际行为、期望行为和定位结果。
5. 必需测试未通过时，相关模块或修改不能标记完成。
6. 性能、面积和时序结论必须绑定输入 commit、配置、workload、命令、工具版本、指标定义和证据路径。
7. 禁止手工伪造测试、综合、时序、性能、覆盖率或实验结果。

## 7. 文档、运行数据与防膨胀

1. 文档按稳定职责、机制、模块、协议和 Lifecycle 组织，不按对话、Agent 或一次性任务组织。
2. Git 保存历史。项目只维护一套当前 Architecture、Design 和 Verification，不创建平行的 `v1`、`v2`、`final` 或备份树。
3. 新增目录、Schema 或抽象前，必须说明其独立职责、生命周期、所有者和长期维护方式。
4. 不创建空目录、空主题文件、推测性占位文档或由生成器维护的第二份处理器模型。
5. 缓存、生成 RTL、临时工作树、波形、原始日志和一次性研究快照进入 Runtime 路径。
6. 可复现结论晋升到正式文档后，删除重复草案前必须取得用户确认。
7. 未经用户确认，不清理遗产材料、缓存、生成物和实验证据。
8. 人类可直接编辑 Architecture、Design 和 Verification。Agent 不从 Schema、索引或缓存反向覆盖这些文件。

## 8. 环境与工具脚本

1. 环境探测、依赖安装、工具配置、平台适配和固定命令入口由项目或 Skill Package 的脚本负责。
2. Agent 优先调用项目声明的脚本，并记录命令、工作目录、退出码、工具版本、日志和证据位置。
3. 脚本缺失或执行失败时，报告准确缺口和恢复条件，不反复猜测命令或临时拼接替代环境。
4. 未经用户明确授权，不修改全局 `PATH`、WSL 配置、系统包管理器、许可证配置或仓库外工具安装。
5. 本文件和通用 Skill 不硬编码本机绝对路径、用户名、处理器专属模块名、信号名或流水级名称。

## 9. 交付要求

每次交付说明：

1. 修改文件和修改范围。
2. 对应的 Architecture、Design 或用户决定。
3. 新增、删除和复用的字段、接口与状态。
4. 关键周期边界、同拍优先级和不变量。
5. 断言、测试和未覆盖范围。
6. 验证命令、工具版本、结果和证据路径。
7. 时序、面积、性能与维护风险。
8. 未解决问题和需要用户决定的事项。

## 10. 禁止事项

1. 禁止未读相关文档直接输出技术结论或修改源码。
2. 禁止用外部项目经验覆盖当前项目事实。
3. 禁止自行补协议、字段、身份保护和保守机制。
4. 禁止为了通过测试扩大 stall、flush、kill 或串行化范围。
5. 禁止在未说明时序风险时引入依赖链、高扇出控制或宽比较网络。
6. 禁止修改未授权路径或执行未授权的外部状态变更。
7. 禁止把 Agent 推荐、默认项或草案写成用户已经批准的事实。
8. 禁止自动覆盖项目现有 `AGENTS.md` 或用户直接维护的正式材料。
